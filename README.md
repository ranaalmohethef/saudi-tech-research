# Saudi Technology Research Data Hub

A data engineering project that collects, cleans, validates, joins, and filters research metadata from Saudi universities to support exploration of technology-related research.

**Team:** Rana Ayman Almohethef · Rana Saad AlHasaniah · Aryam Saad Alotaibi

## 1. Project Question

> What technology-related research is being published by Saudi universities, and how is it changing over time?

The current included sources cover KAUST, KFUPM, and KSU. PNU work is preserved for audit but excluded from the final dataset because the reviewed enrichment could not be reliably mapped back to the original PNU records.

## 2. Pipeline

```text
Extract → Profile & Clean → Validate → Join → Technology Filter → Transform → final.csv
```

The active implementation is in `src/` and is used by both the notebooks and `main.py`. The notebooks document the analysis and decisions; they do not maintain separate copies of the validator or filter logic.

### Data-quality rules

- Raw source files are never modified.
- Missing required values are **not silently dropped during cleaning**; they remain available for Task 3 rejection reporting.
- A partial date such as `2024` or `2024-03` does **not** become an invented full date. `publication_date` is populated only when year, month, and day are known.
- DOI values are normalized to bare lowercase form before validation.
- Duplicate `research_id` values fail validation/join checks rather than being silently removed.
- Technology keywords use whole-word matching so `iot` does not match `riot` and substring fragments do not create false positives.

## 5. Data Sources

### KAUST

- **2023:** KAUST repository CSV snapshot.
- **2024–2025:** Crossref REST API snapshot filtered by KAUST ROR.
- Repository records are scoped to 2023 during cleaning.
- Crossref records are scoped to 2024–2025 through both extraction settings and cleaning settings.
- Partial source dates keep their year in `publication_year`, but `publication_date` stays empty unless a complete date exists.

### KFUPM

The active source is **KFUPM Pure**, harvested through OAI-PMH in MODS format.

| Item | Value |
|---|---|
| Endpoint | `https://pure.kfupm.edu.sa/ws/oai` |
| Years | 2023–2026 |
| Department | `Department of Computer Engineering` |
| Department field | Pure organisational unit |
| Cleaned after department/year/genre scope | 441 |
| Validated | 415 |
| Rejected because DOI is missing | 26 |

The important validation behavior is that the 26 missing-DOI records are **kept through cleaning and appear in `KFUPM_rejected.csv`**. They are not silently removed before Task 3.

The older 48-record KFUPM EPrints thesis collection is not used by the active pipeline. It is retained only as historical source evidence.

### KSU

KSU uses annual institutional JSON files for 2023, 2024, and 2025.

Known source limitations:

- `publication_year` is the annual dataset year because individual records do not publish a usable publication date.
- `url` is the annual dataset download URL because KSU does not provide a per-publication page in these files.
- The 2024 file does not contain DOI/abstract fields for normal rows, so most of that year's records fail the mandatory DOI rule.
- The original 2025 JSON contains one invalid `backslash + literal tab` sequence. `src/extract.py` repairs this into `data/interim/ksu_publications_2025_repaired.json` while leaving the raw file unchanged.
- Reviewed manual enrichment is applied only to explicitly approved records and never overwrites an existing conflicting DOI.

## 6. Shared Schema

The shared dataset uses these 13 columns in this order:

| Column | Required | Rule |
|---|---|---|
| `research_id` | Yes | Non-empty and unique |
| `university` | Yes | Must match the source university |
| `title` | Yes | Non-empty |
| `authors` | Yes | Non-empty |
| `publication_year` | Yes | Whole year from 2023–2026 |
| `publication_date` | No | Real `YYYY-MM-DD` when available; must agree with `publication_year` |
| `abstract` | No | Text when available |
| `research_field` | No | Text when available |
| `tech_category` | No | Category when assigned |
| `journal` | No | Venue when available |
| `doi` | Yes | Bare DOI in `10.xxxx/...` form |
| `url` | Yes | Complete HTTP/HTTPS URL with a hostname |
| `source` | Yes | Non-empty source identifier |

Missing optional fields are allowed. Missing required fields are rejected with their reasons preserved in the source-specific rejection CSV.

## 7. Validation

Validation is implemented once in `src/schema.py` and checks:

- required fields,
- university value,
- integer year within the project range,
- complete HTTP/HTTPS URL,
- DOI syntax,
- real `YYYY-MM-DD` dates,
- date/year consistency,
- unique `research_id` values.

Validation is structural. It does not independently prove that a DOI belongs to a title, that an affiliation is correct, or that a paper is truly technology-related.

## 8. Technology Filter

The filter implementation is in `src/transform.py` and the keyword list is in `config.yaml`.

Rules:

1. Case-insensitive.
2. Hyphen/underscore/whitespace differences are normalized.
3. Whole-word matching is used.
4. `computer vision syndrome` is removed before technology matching because it is an eye condition rather than computer-vision research.
5. Every validated record receives an audit result.

Search fields differ because the source fields differ:

- **KAUST/KFUPM:** `title` + `abstract`.
- **KSU:** raw `Article Title` + `Author Keywords`.

For KSU, keyword evidence is computed from raw columns but the actual selection is applied only **after schema validation** by stable `research_id`.

Audit files:

```text
data/interim/KSU_technology_review.csv
data/interim/ksu_provenance.json
data/processed/technology_filter/filter_review.csv
data/processed/technology_filter/no_keyword_match.csv
```

A keyword match means “candidate for technology research,” not a confirmed subject classification.

## 9. Transformations

`data/processed/final.csv` contains the 13 schema columns plus:

| Rule | Transformation | Output |
|---|---|---|
| R1 | Standardize `publication_year` to pandas nullable integer | `publication_year` |
| R2 | Flag whether a DOI is populated | `has_doi` |
| R3 | Count words in the abstract | `abstract_word_count` |
| R4 | Keep records matching the shared technology filter | filtered rows |

Because DOI is mandatory at validation time, `has_doi` is expected to be `True` for every accepted final record. It is retained because it is part of the agreed Task 4 transformation table.

## 10. PNU Exclusion

The preserved PNU work is excluded because Crossref enrichment results were assigned back to filtered PNU rows by DataFrame index rather than by a stable record identifier. After filtering, the original PNU index and the new Crossref result index no longer represented the same records, which caused metadata to be attached to the wrong publications.

Additional reviewed problems included unverified first-result API matches, duplicated DOI groups, year inconsistencies, and unrestricted substring keyword matching.

The original PNU work is preserved under:

```text
notebooks/excluded_pnu/
```

It should not be merged into `final.csv` until enrichment is rebuilt using a stable key and verified candidate matching.

## 12. Run the Project

Install dependencies:

```bash
python -m pip install -r requirements.txt
```

Run the full pipeline:

```bash
python main.py
```

Run tests:

```bash
pytest -q
```

or:

```bash
python -m pytest -q
```

Run only selected sources:

```bash
python main.py --sources kaust
python main.py --sources kaust kfupm
```

A partial-source run does **not** overwrite the shared `final.csv`. It writes a source-specific file such as `final_kaust.csv`.

To intentionally skip technology filtering:

```bash
python main.py --no-tech-filter
```

This writes `final_no_tech_filter.csv`, so the normal technology-filtered `final.csv` is not overwritten.

## 14. Known Limitations

- Source coverage is uneven across universities and years, so record counts must not be interpreted as a university ranking.
- KSU is institution-wide while KFUPM is limited to one department.
- `tech_category` is not yet populated; the current technology filter only selects candidates.
- Publication-year meaning differs by source (repository date, Crossref publication date, or annual reporting file).
- DOI is mandatory by team schema, so legitimate research without a DOI is rejected.
- Cross-university DOI duplicates may be legitimate co-authored papers and are kept for review rather than automatically removed.
- Publication/retraction status is not fully validated by the structural schema.
